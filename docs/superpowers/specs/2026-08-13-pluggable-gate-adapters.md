# Agent Arena v0.3: Pluggable gate adapters

## Summary and scope

Make the review/validation/decision gate a pluggable adapter, exactly like the
writer layer already is. v0.3 delivers the gate adapter contract, converts
Cursor into the first adapter without behavior change, and adds an OpenCode
gate adapter with a generated project-level gate policy. Every other property
of the formal path stays: detached immutable review snapshot, SHA-bound
validation report, SHA-bound decision record, fail-closed integrity checks,
and the best-effort relay. A writer-gate profile becomes the free combination
`WRITER-GATE` (for example `pi-opencode`), while existing `WRITER-cursor`
profiles and v0.2 manifests keep working unchanged.

Out of scope: new gate CLIs beyond OpenCode (Codex has no project-level policy
file and Agy policy is global, not per project — each needs its own design
pass), automatic gate migration of live runs, and any live-model smoke in the
hermetic suite.

## Profiles and usage

```bash
agent-arena start RUN_ID --repo PATH --profile pi-cursor          # v0.2 form, unchanged
agent-arena start RUN_ID --repo PATH --profile pi-opencode        # v0.3 free combination
agent-arena start RUN_ID --repo PATH --writer pi --gate opencode  # explicit two-dimension form
```

- `--profile NAME` accepts both `WRITER-GATE` forms; `--writer`/`--gate` split
  the selection explicitly and require each other when either is given.
- `--gate` defaults to `cursor`, so every v0.2 command line behaves identically.
- The gate adapter owns: `probe` (local availability), `capabilities`
  (declared flags), `launch` (start the reviewer in the pane), and `policy`
  (generate the project-level gate policy inside the review snapshot and print
  the binding manifest: policy file path, wrapper path, and both SHA-256
  hashes). The `.agent-arena-gate` wrapper stays universal: it only execs the
  Arena command for `status|validate|decision|relay`.
- A run records `gate_adapter` in both the run manifest and the review
  manifest. A legacy manifest or review manifest without the field resolves to
  `cursor` and to the current review.tsv hash fields.

## Walkthrough round 1: user stories and acceptance criteria

1. An operator can start a run with any writer-gate combination that has local
   executables, for example `start RUN --profile pi-opencode`.
2. A reviewer pane always launches the gate recorded in the manifest, never a
   guessed one.
3. The gate policy inside the review snapshot is generated by that gate's own
   adapter and is bound to the review manifest by hash.
4. Existing v0.2 runs, manifests, profiles, and commands keep working without
   migration.

| ID | Acceptance criterion | Test intent |
| --- | --- | --- |
| AC1 | Every gate adapter answers `probe`, `capabilities`, `launch`, and `policy`; the Cursor adapter, converted, keeps the current policy content, wrapper, and hash fields byte-identical apart from the adapter-driven generation path. | full-suite regression + adapter contract fixture |
| AC2 | `--writer W --gate G` and `--profile W-G` resolve identically; `--gate` alone or `--writer` alone fails; unknown gate or gate without executable fails before any state is created. | CLI matrix fixture |
| AC3 | A manifest without `gate_adapter` resolves to `cursor`; a review manifest without `gate_adapter` resolves to `cursor` and its existing two hash fields stay authoritative. | legacy fixture |
| AC4 | `submit` generates the gate policy through the manifest's gate adapter, binds policy path + wrapper path + hashes in review.tsv, and the integrity check verifies exactly those declared paths. | submit/integrity fixture under `pi-opencode` |
| AC5 | The reviewer pane dispatches the manifest `gate_adapter`; relay safety and role/mode tags are unchanged. | pane dispatch fixture |
| AC6 | The OpenCode gate adapter emits a project-level `opencode.json` gate agent that allows read/glob/grep and bash (the wrapper is a bash target), denies edit/webfetch/websearch/task/question/external_directory, and routes wrapper commands to Arena. | opencode-gate policy fixture |
| AC7 | `doctor` lists every available gate and its writer-gate profiles; zero available gates makes `doctor` fail. | doctor matrix fixture |

## Walkthrough round 2: technical trace

`start` → profile resolver splits `WRITER-GATE` into writer adapter + gate
adapter (or reads `--writer`/`--gate`) → probes both → clean integration root →
writer worktree + manifest with `gate_adapter` → tmuxp session exports
`ARENA_GATE_ADAPTER` and adapter-specific env. `submit` → clean writer HEAD →
detached snapshot → `adapters/<gate>.sh policy <worktree>` → writes the gate
policy file + the universal `.agent-arena-gate` wrapper → binds
`gate_adapter`, `gate_policy_path`, `gate_policy_hash`, `gate_wrapper_hash` in
review.tsv → reviewer pane respawn (best-effort, AC11 of v0.2 unchanged).
`pane.sh reviewer` reads `gate_adapter` from the manifest and execs
`adapters/<gate>.sh launch` with `ARENA_GATE_WORKSPACE`/`ARENA_GATE_PHASE`
(generalized from `ARENA_CURSOR_*`). `validate`/`decision`/`status` run the
same integrity check parameterized by the declared gate policy path.

Gate adapter contract (mirrors the writer contract):

```text
adapters/<gate>.sh probe        # exit 0 iff the gate CLI is locally available
adapters/<gate>.sh capabilities # stable line-oriented flags
adapters/<gate>.sh launch       # exec the gate CLI in the review pane (ARENA_GATE_* env)
adapters/<gate>.sh policy WT    # generate gate policy files inside WT and print:
                                #   gate_policy_path<TAB>gate_policy_hash
                                #   gate_wrapper_path<TAB>gate_wrapper_hash
```

The Cursor adapter's `policy` writes the current `.cursor/cli.json` (the
permissions-only schema) and `.agent-arena-gate`, producing identical content
and hashes to v0.2. The OpenCode gate adapter writes `<WT>/opencode.json` with
an `arena_gate` agent whose permissions allow read/glob/grep plus
`./.agent-arena-gate {status,validate,decision,relay} *` and deny
write/edit/webfetch/websearch/task/question/external_directory/bash
(execution is possible only through the wrapper); `.agent-arena-gate` is the
wrapper. `arena_review_snapshot_is_intact` switches its generated-file check
from the hard-coded `.cursor/cli.json` to the declared `gate_policy_path`
(ignore rules still apply per path).

The OpenCode gate agent cannot express a command-level allowlist: `bash` is a
binary tool permission, and the wrapper itself is a bash command. The policy
therefore allows read/glob/grep/bash and denies edit/webfetch/websearch/task/
question/external_directory; the reviewer prompt restricts bash to the
wrapper, and the post-run integrity check closes any tampering (same
enforcement model as the Cursor deny-list lesson: deny is the hard boundary,
unlisted semantics are advisory, the audit close is the integrity check).

## Walkthrough round 3: integration and errors

Unknown gate, gate without executable, gate/writer probe failure, and
ambiguous `--writer`/`--gate` combinations fail closed before worktree or tmux
creation. A legacy v0.1/v0.2 manifest resolves `gate_adapter=cursor` and never
silently changes gate on resume. A review manifest whose declared gate policy
path is missing, replaced, symlinked, or hash-changed fails validate/decision/
status exactly as today. A gate adapter that prints an unparseable or
hash-invalid policy manifest fails submit before review.tsv is written. The
OpenCode gate policy denies edit/webfetch/websearch/task/question/
external_directory and allows bash only because the wrapper is a bash target;
the wrapper remains the sanctioned execution path and the post-run integrity
check remains the audit close.

## Testing, drift, risk, and rollback

Hermetic tests only: fake gate adapters, fake CLIs, temporary repositories,
private tmux sockets. No model or network call. The full v0.2 suite must stay
green on the converted Cursor adapter before any new gate is added (AC1
regression gate). OpenCode gate live smoke (an authenticated session where the
OpenCode gate rejects a write and a wrapper-only gate flow succeeds) is a
post-release manual item, like v0.2's Gate 4.

Drift risk: the gate policy schema is CLI-version-sensitive (the v0.2 Gate 4
smoke already survived one auto-update); the OpenCode gate policy follows the
same `opencode.json` schema the writer policy already uses, which the CLI
resolves today. Risk: a second gate doubles the policy-maintenance surface and
the interactive-mode semantics of an unlisted command vary per CLI; both are
recorded, not hidden. Rollback: keep `--gate cursor` or the legacy profile
form; existing worktrees, snapshots, reports, and decisions are untouched.
